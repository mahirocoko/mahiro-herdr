## Honest Feedback

Three friction points were clear. First, delegation cost time without establishing a necessary independent capability; there was no browser task and the scope was already anchored in two local owners. Second, fresh-install tests hid the existing-install upgrade problem. A passing configure test did not prove that Mahiro's real saved configuration would acquire the new row. Third, the initial report combined fixture support, runtime support and readiness too confidently. Linux handling contradicted the stated boundary, PID liveness was weaker than PID-reuse protection, and optional discovery could consume the global deadline. Main's audit corrected those claims and behavior, but it should have framed those acceptance counterexamples before dispatch. The good outcome came from small real probes and exact owner preservation, not from the length of the report.

## Lessons Learned

- Test an existing applied snapshot, including applied-only settings, before claiming a configuration extension upgrades safely.
- Optional metadata collection needs its own bounded budget and must clear its token without suppressing primary metadata.
- A process liveness check is not an atomic ownership or PID-reuse proof.
- Main-first for routine mahiro-herdr CLI/config/runtime work is now directly human-approved and recorded in project memory.
- No separate reference-learning file: these decisions are captured in the current source/docs and approved project memory rather than duplicated as candidate doctrine.
